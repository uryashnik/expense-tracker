# Код-ревью

Регламент ревью Pull Request в этом репозитории. `CLAUDE.md` описывает, **как писать** код и коммиты; этот файл — **что проверяет ревьюер** перед аппрувом и как оформляет замечания.

Применяется к любому PR в `main` — и к ревью человеком, и к автоматическому от `.github/workflows/claude-code-review.yml`. Единственный источник правил — `CLAUDE.md` в корне и `apps/*/CLAUDE.md`: замечание должно опираться на них, а не на личный вкус ревьюера.

## Зачем это нужно

CI в проекте нет — `.github/workflows` содержит только два workflow с Claude. Сборка, линт и типы прогоняются локально автором, а `main` защищена от прямых коммитов. Значит, **ревью — единственный барьер перед `main`**, и проверка «собирается ли оно вообще» входит в обязанности ревьюера наравне с чтением логики.

## Порядок ревью

1. **Заголовок PR.** Мержим squash-мержем, поэтому заголовок становится сообщением коммита в `main` и обязан проходить commitlint: `type(scope): описание`, scope из `web`, `api`, `shared`, `repo`, `db`, `deps`. Проверяется одной командой:

   ```bash
   echo 'feat(web): add home dashboard with paginated transactions' | npx commitlint
   ```

2. **Состав изменений — до чтения кода.** Ревью начинается с карты диффа, а не с первого файла:

   ```bash
   git diff --name-status main...<branch>   # что добавлено, что изменено
   git diff --stat main...<branch>          # объём
   git log --oneline main..<branch>         # состав коммитов
   ```

   Здесь же видно, разбита ли работа по scope (схема и миграция → `db`, транспортные типы → `shared`, модуль Nest → `api`, конфиги → `repo`) и не примешаны ли к фиче посторонние правки.

3. **Тело PR против диффа.** Описание должно быть написано по фактическому диффу: изменения контракта — фрагментом кода, а не пересказом; отдельно — решения, которых не видно из диффа, попутно исправленные дефекты, как проверено и **что не проверялось**, что намеренно не вошло. Пункт «как проверено» без «чего не проверяли» — повод спросить, а не додумать.

4. **Локальная проверка.** Ветку выкачиваем и прогоняем то же, что должен был прогнать автор:

   ```bash
   npm install
   npm run prisma:generate -w @expense-tracker/api   # обязателен: src/generated/prisma не в гите
   npm run lint && npm run typecheck && npm run build
   ```

   Если в PR затронута схема Prisma — ещё `npm run db:up` и `npm run prisma:migrate -w @expense-tracker/api` на чистой базе. `typecheck`, упавший сотнями ошибок об отсутствующем модуле, — это не сломанный PR, а забытый `prisma:generate`.

5. **Чтение кода** — по чек-листам ниже: сначала общий, затем по затронутым областям.

6. **Актуальность ветки.** Ветка обязана быть свежей относительно `main`; расхождение автор решает `git rebase main`, а не merge-коммитом внутрь ветки. Merge-коммит из `main` в ветку — блокирующее замечание.

## Формат замечаний

Три уровня, и уровень указывается явно — иначе автор не понимает, что чинить обязательно:

- **Блокирует** — без исправления не мержим. Это: нарушение правил из `CLAUDE.md`, дыра в проверке владения или аутентификации, расхождение контракта между `api` / `shared` / `web`, не прогнанные (или падающие) `lint` / `typecheck` / `build`, заголовок PR, не проходящий commitlint.
- **Стоит поправить** — не блокирует, но остаётся в PR как задача автора: дублирование, которое скоро разъедется, неудачное имя, пропущенный край в логике без прямого вреда.
- **nit** — вкусовщина, автор вправе не согласиться. Помечать явно, чтобы не тратить раунд на спор.

Что должно быть в комментарии:

- **Ссылка на правило или на код**, а не «мне кажется». Формат `apps/api/src/transactions/transactions.service.ts:42` кликабелен и не требует поиска.
- **Сценарий поломки** для блокирующего замечания — конкретный вход и конкретный неверный результат. «Здесь возможна ошибка» не является замечанием.
- **Одно замечание — один комментарий.** Список из шести пунктов в одном треде невозможно разрешать по частям.

Отдельно: замечание вида «а вот здесь сделано не так, как я привык» проверяется по `CLAUDE.md`. Если правило там есть — ссылаемся на него. Если правила нет, а решение осознанное — обсуждаем в PR и, договорившись, **правим `CLAUDE.md` отдельным коммитом `docs(repo):`**, а не оставляем договорённость в треде, который никто больше не прочитает.

## Общий чек-лист

- [ ] Заголовок PR проходит commitlint; описание в нижнем регистре, без точки, в повелительном наклонении.
- [ ] Одна ветка — одна фича; имя ветки `<тип>/<scope>-<описание>`.
- [ ] Коммиты разбиты по scope, а не свалены в один; посторонние правки вынесены отдельно.
- [ ] `lint`, `typecheck`, `build` прогнаны и зелёные.
- [ ] Ветка актуальна относительно `main`, merge-коммитов внутрь ветки нет.
- [ ] Новых зависимостей нет — либо они обоснованы в теле PR. Версии фиксируются точно (`save-exact=true`), диапазоны (`^`, `~`) в `package.json` не появляются.
- [ ] Изменения `package-lock.json` соответствуют изменениям `package.json`, а не приехали от чужой версии npm.
- [ ] В диффе нет сгенерированного и локального: `apps/api/src/generated/prisma`, `.env`, `dist`, `.next`, `.turbo`, содержимое `.idea`.
- [ ] Секретов, реальных токенов и дампов в диффе нет; новая переменная окружения добавлена в соответствующий `.env.example`.
- [ ] Документация обновлена вместе с кодом: правило, которое ревьюеру пришлось объяснять в треде, оседает в `CLAUDE.md`.

## `apps/api`

- [ ] **Слои соблюдены**: `PrismaService` трогает только репозиторий; сервис — доменная логика и маппер; контроллер — разбор запроса и вызов маппера, бизнес-правил в нём нет.
- [ ] **Prisma-сущность не уходит в ответ.** Тип ответа собирается маппером (`toCategory` / `toTransaction` / `toAuthUser`). Утечка `passwordHash` или `Decimal` в JSON — блокирует.
- [ ] **Проверка владения на каждом методе**: `userId` из `@CurrentUser()`, `assertOwnership` в сервисе. Чужой и несуществующий id дают **одинаковый 404** — 403 подтверждает существование записи. Ссылки на чужие сущности (`categoryId` в транзакции) проверяются отдельно.
- [ ] **Новый роут закрыт по умолчанию.** `JwtAuthGuard` глобальный, `@UseGuards` не нужен; появившийся `@Public()` — всегда предмет обсуждения в PR, а не деталь диффа.
- [ ] **DTO** лежат в `apps/api`, валидируются class-validator и не дублируют в себе тип ответа. `@Type(() => Number)` для query не нужен — работает `enableImplicitConversion`. Дефолты задаются инициализатором поля.
- [ ] **Литеральные подпути объявлены выше параметрических** (`@Get('summary')` до `@Get(':id')`) — иначе роут уедет в `:id` и вернёт 400.
- [ ] **Формат ошибки не изменён в обход контракта**: правка `http-exception.filter.ts` тянет за собой `packages/shared/src/api.ts` и `apps/web/src/shared/api/client.ts`.
- [ ] **Деньги и даты**: `amount` положителен, направление задаёт `type`; ограничение `maxDecimalPlaces: 2` совпадает со схемой `Decimal(12, 2)`; границы периодов считаются в UTC.
- [ ] **Ничего существенного не перенесено в обработчики событий**: `EventBus` работает fire-and-forget, исключение в хендлере не откатит команду и не всплывёт. Обработчик ловит свои ошибки сам.
- [ ] **Новый ресурс сделан в простом стиле** service + repository. CQRS остаётся только в `auth`; перевод нового модуля на шину — блокирующее замечание, если это не обсуждено в PR.
- [ ] **Обязательные переменные окружения читаются через `getOrThrow`** — приложение падает на старте, а не отдаёт 500 на первом запросе.

## `apps/web`

- [ ] **Слои FSD**: импорт только вниз (`app → widgets → features → entities → shared`), соседи одного уровня связываются слотами. Импорт вида `@/features/auth-login/ui/login-form` мимо `index.ts` — блокирует.
- [ ] **Страницы тонкие**: роутинг и композиция, без бизнес-логики.
- [ ] **Сеть только с сервера**: серверные компоненты и `'use server'`-экшены через `shared/api/client.ts`. `fetch` из браузера и появившийся `NEXT_PUBLIC_API_URL` — блокирует; клиентский слой данных (TanStack Query и т.п.) в проекте не заводим.
- [ ] **Экшен валидирует вход сам** (`schema.safeParse` над сырыми `form.getValues()`), возвращает `ActionErrorState | { status: 'success' }` и не бросает; после мутации — `revalidatePath('/')`.
- [ ] **`getAuthHeaders()` и `redirect()` вызываются вне `try/catch`**: `redirect()` бросает `NEXT_REDIRECT`, и `catch` превратил бы переход в ошибку запроса.
- [ ] **Zod-схема зеркалит DTO**: ограничения полей продублированы вручную, и при изменении контракта правятся обе стороны.
- [ ] **Запросы страницы не выстроены в водопад**: параллельные данные идут одним `Promise.all` на уровне страницы, а не внутри вложенных серверных компонентов.
- [ ] **Состояние списка живёт в query-строке**, а не в `useState`; смена фильтра сбрасывает `page`.
- [ ] **shadcn/ui после `npx shadcn add`**: `cn` импортируется из `@/shared/lib/utils` (не из пакета `cn`), `accent`/`accent-foreground` заменены на `secondary`, примитивы берутся из единого пакета `radix-ui`.
- [ ] **Токены компонента есть в `@theme`** (`globals.css`): отсутствующий токен Tailwind v4 молча не сгенерирует — компонент откроется без фона, и сборка об этом не скажет.
- [ ] **Next 16**: `await cookies()`, `searchParams` как `Promise`, собранный из частей путь приведён `as Route`.
- [ ] **`import 'server-only'` не снят** с `entities/session/lib/session.ts`.

## `packages/shared` и контракт API

Контракт живёт в трёх местах, и они правятся вместе, но **разными коммитами**: тип ответа — `packages/shared/src/api.ts` (`shared`), DTO и правила — `apps/api` (`api`), zod-схема формы — `apps/web` (`web`).

- [ ] Все три места согласованы; ни одно не забыто.
- [ ] В `shared` уехали только транспортные типы ответов — не DTO запросов, не бизнес-правила, не хелперы одного приложения.
- [ ] `dependsOn: ["^build"]` у задач `dev`, `lint`, `typecheck` в `turbo.json` на месте: `packages/shared` потребляется как собранный `dist`, а не как исходники.
- [ ] Изменение контракта показано в теле PR фрагментом диффа — ревьюер должен увидеть новую сигнатуру глазами.

## `db` — схема и миграции

- [ ] Схема и миграция идут отдельным коммитом со scope `db`, код Nest — своим со scope `api`.
- [ ] Миграция приложена в `prisma/migrations` и применяется на чистой базе.
- [ ] Уже применённая миграция не отредактирована задним числом — изменение оформлено новой.
- [ ] Идентификаторы — `uuid(7) @db.Uuid`, имена таблиц — `@@map` в snake_case множественном.
- [ ] Индексы заведены под реальные запросы нового кода, а не «на всякий случай».
- [ ] Последствия `onDelete: Cascade` осознаны и описаны в PR: удаление категории уносит её транзакции.
- [ ] Блок `datasource` не содержит `url` — в Prisma 7 это ошибка валидации P1012.

## `repo` и `deps`

- [ ] Правки корневых конфигов, тулинга и документации идут отдельным коммитом со scope `repo`, обновления зависимостей — `deps`.
- [ ] Ограничения по версиям соблюдены: TypeScript 5.9.x, ESLint 9.x, lint-staged 16.x, Tailwind v4 без `tailwind.config.js`. Обновление, ломающее любое из них, требует обоснования в PR.
- [ ] Отключение `consistent-type-imports` для `apps/api` не «прибрано»: оно нужно **в двух местах** — в `apps/api/eslint.config.mjs` и блоком с `ignores: ['apps/api/**/*.ts']` в корневом конфиге.
- [ ] Изменения хуков (`.husky`), commitlint и lint-staged описаны в PR — они меняют работу всех остальных.

## Что не является замечанием

Осознанные решения проекта. Возражать против них можно, но отдельным обсуждением, а не строчкой в ревью чужой фичи:

- **Два стиля модулей в `apps/api`.** CQRS в `auth` оправдан побочными эффектами; остальные модули — service + repository. Это не «недоделанная унификация».
- **Отключённый `consistent-type-imports` для `apps/api`.** `import type` стирает метаданные, нужные Nest для DI и `ValidationPipe`.
- **Отсутствие клиентского слоя данных в `apps/web`.** Запросы идут с сервера намеренно.
- **`API_URL` без `NEXT_PUBLIC_`.** Переменная серверная по замыслу.
- **3 high-уязвимости `deepmerge-ts` в `npm audit`.** Транзитивная зависимость `@prisma/config`; единственный «фикс» от npm — откат на Prisma 6.
- **Блок в `apps/web/AGENTS.md`.** Его пишет сам `next dev`; удаление из диффа лишь воссоздаёт незакоммиченное изменение.
- **Отсутствие тестов.** Их пока нет во всём репозитории — требовать их в конкретном PR некорректно. Когда появятся, добавим задачу `test` в `turbo.json` и скрипты в пакеты, и этот пункт уйдёт отсюда в чек-лист.

## Аппрув и мерж

- Аппрув означает: правила соблюдены, `lint` / `typecheck` / `build` проверены ревьюером локально, блокирующих замечаний нет.
- Блокирующие замечания закрывает автор — ревьюер не дописывает код в чужую ветку.
- Мерж — **squash**, заголовок PR становится сообщением коммита. После мержа ветка удаляется, в том числе локально: `git branch -d <branch>`.
- `main` не откатываем и не переписываем (`push --force` запрещён). Ошибка, доехавшая до `main`, чинится новым PR — `fix(...)` или `revert`.
