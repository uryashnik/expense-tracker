# Коммит изменений

Правила формата и разбивки — в `CLAUDE.md` (разделы «Коммиты», «Ветки и Pull Request»). Ниже — порядок действий.

## 1. Осмотреть состояние

Одним вызовом:

```bash
git status --short && git branch --show-current && git log --oneline -5
git diff --stat HEAD && git diff HEAD
```

Смотреть **весь дифф**, а не только имена файлов: сообщение пишется по фактическому изменению. Если есть незатреканные файлы — проверить, что они не мусор (`.env`, сборка, `apps/api/src/generated`).

## 2. Проверить ветку

`main` защищена от прямых коммитов. Если текущая ветка `main` — не коммитить, а сообщить об этом и предложить ветку по правилам проекта:

```bash
git switch -c <тип>/<scope>-<краткое-описание>   # feat/web-home-screen, fix/api-auth-cookie-expiry
```

Создавать ветку только с согласия пользователя.

## 3. Разбить на коммиты по scope

**Один коммит — одно изменение по смыслу.** Если дифф задевает несколько слоёв, разбить по scope:

| Что менялось                                                   | scope    |
| -------------------------------------------------------------- | -------- |
| `apps/web/**`                                                  | `web`    |
| `apps/api/**` (кроме Prisma)                                   | `api`    |
| `packages/shared/**`                                           | `shared` |
| `apps/api/prisma/**`, схема и миграции                         | `db`     |
| корневые конфиги, тулинг, документация, `.claude/**`           | `repo`   |
| `package.json`/`package-lock.json` при обновлении зависимостей | `deps`   |

Другие значения scope commitlint отклонит (`scope-enum`, уровень error).

Правки не по задаче (починка чужого бага, конфиг тулинга) — отдельным коммитом, не примешивать к `feat`.

Индексировать поимённо: `git add <файлы>`. Не использовать `git add -A`/`git add .`, когда коммитов больше одного.

## 4. Написать сообщение

Формат: `type(scope): описание`

- Тип: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`, `perf`, `style`, `revert`.
- Описание — в нижнем регистре, в повелительном наклонении, без точки в конце: `feat(api): add transactions module`.
- Описание на английском — как в существующей истории (`git log --oneline` для сверки стиля).

Проверить до коммита:

```bash
echo 'feat(api): add transactions module' | npx commitlint
```

Молчаливый выход = формат в порядке.

## 5. Закоммитить

Сообщение передавать heredoc'ом, чтобы не терять переносы, и добавлять футер атрибуции, заданный правилами текущей сессии (`Co-Authored-By` + `Claude-Session`):

```bash
git commit -F - <<'EOF'
feat(api): add transactions module

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
Claude-Session: <URL сессии>
EOF
```

Тело коммита — только если из заголовка не ясно «зачем». Пересказывать дифф в теле не нужно.

## 6. Отработать хуки

`pre-commit` гоняет lint-staged (ESLint --fix + Prettier), `commit-msg` — commitlint.

- **commitlint упал** — исправить формулировку, повторить коммит.
- **ESLint --fix изменил файлы** — коммит проходит уже с исправлениями, но если хук упал на неисправимой ошибке, чинить её и добавлять исправление **в тот же коммит** (`git add` + повторный `git commit`), а не отдельным «fix lint».
- Никогда не обходить хуки (`--no-verify`) — они и есть единственная проверка, CI в проекте нет.

## 7. Отчитаться

`git status --short` и `git log --oneline -<n>` — показать пользователю, что получилось. Не пушить и не открывать PR, если об этом не просили.

## Чего не делать

- Не коммитить `.env`, содержимое `apps/api/src/generated`, артефакты сборки.
- Не менять `git config`, не подписывать коммиты чужим автором.
- Не делать `commit --amend` и `push --force` для уже опубликованных коммитов.
- Не подтягивать в коммит несвязанные изменения ради «чистого рабочего дерева» — оставить их незатреканными и сказать об этом.
