# Создание Pull Request

Правила — в `CLAUDE.md` (разделы «Ветки и Pull Request (GitHub Flow)» и «Оформление Pull Request»). Ниже — порядок действий.

## 0. Разобрать аргументы

`/pr [title] [base-branch]` — оба аргумента позиционные и опциональные:

| Позиция | Аргумент      | Что задаёт    | Если не передан                          |
| ------- | ------------- | ------------- | ---------------------------------------- |
| 1       | `title`       | заголовок PR  | сгенерировать самому по диффу и коммитам |
| 2       | `base-branch` | базовая ветка | `main`                                   |

Заголовок содержит пробелы, поэтому границу между аргументами определять так:

1. Аргументов нет — заголовок сгенерировать, база `main`.
2. Заголовок title коммита (`type(scope): title`) и тянется до конца строки — **кроме** случая, когда последний токен без пробелов оказался существующей веткой на `origin`; тогда он и есть база, а заголовок — всё до него.

Проверять принадлежность последнего токена ветке, а не гадать:

```bash
git ls-remote --exit-code --heads origin <токен>
```

Если разбор всё равно неоднозначен (последний токен похож и на ветку, и на часть описания) — спросить пользователя, а не выбирать молча.

Дальше:

- **Заголовок передан** — всё равно прогнать через commitlint (шаг 3). Если формат не проходит, не переписывать молча: показать ошибку commitlint и предложенный исправленный вариант, дождаться подтверждения.
- **Заголовок не передан** — составить самому строго по конвенции: `type(scope): описание`, из набора типов и scope проекта, в нижнем регистре, в повелительном наклонении, без точки. Один PR — одна фича, поэтому заголовок описывает ветку целиком, а не последний коммит.
- **База передана** — убедиться, что ветка есть на `origin` (той же командой `git ls-remote`); нет — сказать пользователю и остановиться, а не откатываться на `main` молча. Во всех сравнениях диффа ниже подставлять её вместо `main`.

## 1. Проверить состояние

```bash
git status --short && git branch --show-current
git remote -v && gh auth status
```

- Текущая ветка — **не** база: с `main` PR не открывают, работа должна лежать в ветке `<тип>/<scope>-<описание>`.
- Незакоммиченные изменения — сначала коммит (скилл `commit`), потом PR. Не коммитить молча по ходу.
- `origin` не настроен или `gh` не авторизован — сказать пользователю и остановиться.
- PR для этой ветки уже открыт (`gh pr view --json number,url,state`) — не создавать второй: обновить существующий через `gh pr edit --title/--body-file` и сказать об этом.

## 2. Актуализировать ветку относительно базы

```bash
git fetch origin
git log --oneline origin/<база>..HEAD    # состав ветки
git log --oneline HEAD..origin/<база>    # чего в ветке не хватает
```

Если база ушла вперёд — расхождение решается `git rebase origin/<база>`, **не** merge-коммитом внутрь ветки. Ребейз делать только с согласия пользователя; при конфликтах остановиться и отдать решение ему.

Запушить ветку: `git push -u origin <ветка>` (после ребейза — `git push --force-with-lease`, только для своей ветки, никогда для базы).

## 3. Заголовок

Формат коммита: `type(scope): описание`. Это не косметика — мержим squash-мержем, заголовок PR становится сообщением коммита в базе и обязан проходить commitlint.

- Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`, `perf`, `style`, `revert`.
- Scope: `web`, `api`, `shared`, `repo`, `db`, `deps`. Если ветка задевает несколько — брать тот, ради которого она заведена (главное изменение), а не перечислять.

Проверить обязательно, до создания PR:

```bash
echo 'feat(web): add home dashboard with paginated transactions' | npx commitlint
```

Молчаливый выход = формат в порядке.

## 4. Собрать фактуру по диффу

**Тело пишется по фактическому диффу, а не по памяти.** До написания прогнать:

```bash
git diff --name-status origin/<база>...HEAD   # что добавлено, что изменено
git diff --stat origin/<база>...HEAD          # объём
git log --oneline origin/<база>..HEAD         # состав коммитов
git diff origin/<база>...HEAD                 # сам дифф
```

Отдельно посмотреть изменения контракта — их в теле показывают фрагментом диффа, а не пересказом:

```bash
git diff origin/<база>...HEAD -- packages/shared apps/api/prisma 'apps/api/src/**/dto/*.ts' 'apps/api/src/**/*.controller.ts'
```

## 5. Прогнать проверки

CI сборку не проверяет, поэтому перед PR — локально:

```bash
npm run lint && npm run typecheck && npm run build
```

Красное чинить до создания PR, а не описывать в теле как известную проблему. Если дифф состоит только из `.md` и на сборку не влияет — проверки можно не гонять, но тогда честно написать об этом в разделе «Как проверено».

## 6. Написать тело

Тело — в файл (`<scratchpad>/pr-body.md`), чтобы не терять разметку. Разделы по `CLAUDE.md`; включать только те, для которых есть содержание, — пустых заголовков не оставлять.

1. **Что и зачем** — абзацем: что делает изменение и **что было до него**. Без «в этом PR добавлено…» — сразу по сути.
2. **Изменения контракта** (API, `packages/shared`, схема БД) — фрагментом диффа в ```diff, ревьюер должен увидеть новую сигнатуру глазами. Контракт не менялся — сказать это одной строкой, это тоже информация.
3. **Решения, которых не видно из диффа** — почему сделано так, а не иначе. Главная ценность описания: код показывает «что», PR объясняет «почему». Каждый пункт — решение + альтернатива, которую отвергли, + причина.
4. **Попутно исправленные дефекты** — отдельным списком, чтобы их не искали в диффе фичи.
5. **Как проверено** — какие команды прогнаны и что проверено вживую, с конкретикой (числа, сценарии). **И чего не проверяли** — умалчивать нельзя.
6. **Что намеренно не вошло** и почему.
7. **Замечания для ревьюера** — сгенерированные файлы в диффе, требуемый порядок мержа, посторонние коммиты в ветке, всё, обо что он споткнётся.

Язык тела — русский, как в существующих PR (`gh pr view <n> --json body -q .body` — сверить тон). Названия файлов, команд и идентификаторов — в бэктиках.

## 7. Создать PR

```bash
gh pr create --base <база> --head <ветка> \
  --title 'feat(web): ...' --body-file <scratchpad>/pr-body.md
```

Черновик — `--draft`, если пользователь просил или работа не закончена.

## 8. Отчитаться

Показать ссылку из вывода `gh pr create` и коротко — заголовок, базу, состав коммитов. Не мержить PR: squash-мерж и удаление ветки делает пользователь.

## Чего не делать

- Не открывать PR из базовой ветки и не пушить в неё напрямую.
- Не мержить и не закрывать PR без явной просьбы.
- Не `push --force` в базу; `--force-with-lease` — только в свою ветку после ребейза.
- Не пересказывать дифф построчно: ревьюер видит его сам, тело объясняет «почему».
- Не писать в «Как проверено» то, что не прогонялось, и не опускать раздел «что не проверялось».
- Не разбавлять PR правками не по задаче — если такие есть, вынести отдельным коммитом и упомянуть в «Попутно исправленных дефектах».
